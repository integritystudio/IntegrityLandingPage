Your AI agent just completed a 14-step workflow. It searched a knowledge base, called three APIs, made a decision, drafted an email, and scheduled a follow-up. It took 8 seconds. Something went wrong in step 9. Good luck figuring out which one that was.

Traditional LLM observability—tracking prompts, completions, and token counts—was designed for request-response interactions. One prompt in, one response out. But AI agents don't work that way. They reason, plan, use tools, loop, backtrack, and make autonomous decisions across multiple steps. The observability tooling needs to match.

This guide covers the instrumentation patterns, debugging techniques, and monitoring strategies you need to keep autonomous AI agents under control in production.

Why Agent Observability Is Different

A standard LLM call is a function: input goes in, output comes out. You log the prompt, the completion, the latency, and the token count. Done. An agent is a program: it has control flow, state, side effects, and non-deterministic branching. The observability challenge is fundamentally different.

Dimension Simple LLM Call Agentic Workflow
Execution model Single request-response Multi-step with branching and loops
Side effects None (text generation only) API calls, database writes, emails, file creation
Failure modes Timeout, rate limit, bad output Reasoning errors, tool misuse, infinite loops, cascading failures
State Stateless Accumulates context across steps
Trace depth 1–2 spans 10–50+ spans per execution
Cost attribution Single model call Multiple model calls + external API costs

The implication: you can't just add more logging to your existing LLM observability setup and call it agent observability. You need a different mental model—one built around execution traces, not request logs.

The Agent Trace Model

An agent execution should produce a single trace with a hierarchy of spans that mirrors the agent's decision-making structure. Think of it as a tree where each node represents a discrete unit of work.

Anatomy of an Agent Trace

Each span captures: start/end time, attributes (model, parameters, results), status (ok/error), and parent-child relationships. The tree structure lets you see both the big picture (how many steps? total latency?) and the details (what did step 3 decide, and why?).

Key Span Types

  • agent.run — Root span encompassing the entire agent execution. Attributes: agent name, version, trigger (user message, cron, webhook), total steps, final status.
  • agent.step — One iteration of the agent's reasoning loop. Attributes: step number, action chosen, reasoning summary (if available).
  • llm.completion — A model call within a step. Attributes: model name, version, token counts (prompt/completion), temperature, latency.
  • tool.call — An external tool invocation. Attributes: tool name, parameters, return status, latency, whether it has side effects.
  • guardrail.check — A safety or policy check. Attributes: rule name, pass/fail, confidence score.

Tool Call Tracing

Tool calls are where agents interact with the real world—and where most failures happen. A tool call that returns stale data, times out, or returns an unexpected schema can derail an entire workflow. Proper tracing makes these failures visible and debuggable.

What to Capture

Side Effects Matter

Always tag whether a tool call has side effects (tool.has_side_effects: true). Read-only tools (search, lookup) can be safely retried. Side-effecting tools (send email, process payment, delete record) cannot. When an agent retries a failed step, knowing which tools are idempotent prevents double-execution disasters.

Common Tool Call Failure Patterns

  • Schema mismatch — The agent passes parameters the tool doesn't expect. Trace the raw parameters alongside the tool's expected schema.
  • Stale data — The tool returns cached or outdated results. Log cache hit/miss and data freshness timestamps.
  • Rate limiting — External APIs throttle the agent. Log HTTP status codes and retry counts.
  • Timeout cascades — One slow tool call eats the agent's total timeout budget. Track per-tool latency as a percentage of total execution time.
  • Hallucinated tools — The agent attempts to call a tool that doesn't exist. Log the attempted tool name before the "tool not found" error.

Multi-Step Workflow Tracing

The hardest part of agent observability isn't capturing individual steps—it's understanding the flow between them. Why did the agent choose step B after step A? Why did it loop back to step 3? Why did it take 14 steps when the task should have taken 4?

Trace the Reasoning, Not Just the Actions

Every agent step should capture not just what the agent did, but why it decided to do it. This means logging the agent's planning output—the "chain of thought" that led to each action choice.

Detecting Pathological Patterns

Without tracing, these patterns are invisible until they cause outages:

  • Infinite loops — The agent keeps retrying the same failed step. Set a max_steps limit and log a warning when the agent exceeds 80% of it.
  • Context window overflow — Each step adds to the conversation history until the context window fills up and the agent starts losing important information. Track cumulative token count across steps.
  • Tool call explosion — The agent makes 47 API calls for a task that should require 3. Monitor tool call count per execution and alert on anomalies.
  • Decision oscillation — The agent alternates between two actions without converging. Track the sequence of action choices and flag repeated patterns.
Quick Win

Add a agent.step.count attribute to your root span and set up an alert when it exceeds your p95 baseline by 2x. This single metric catches infinite loops, runaway tool calls, and most "agent gone sideways" scenarios before they become expensive.

Key Metrics for Agent Monitoring

Standard LLM metrics (tokens/sec, time-to-first-token, p99 latency) still matter, but agents need additional metrics that capture decision quality and workflow efficiency.

Execution Metrics

  • Steps per execution — How many reasoning iterations before completion? Trending upward signals growing complexity or degradation.
  • Tool calls per execution — Total external calls. High counts mean high cost and high latency.
  • End-to-end latency — Total wall-clock time from trigger to final response. Break down into LLM time vs. tool time vs. overhead.
  • Token efficiency — Total tokens consumed divided by task complexity. A simple lookup shouldn't cost 50K tokens.

Quality Metrics

  • Task completion rate — Percentage of agent runs that successfully complete the intended task (vs. erroring out, timing out, or requiring human escalation).
  • Tool call success rate — Percentage of tool invocations that return usable results. A drop here often precedes a drop in task completion.
  • Guardrail trigger rate — How often safety checks fire. A sudden spike means the agent is generating more risky outputs.
  • Human escalation rate — Percentage of tasks that require human intervention. Decreasing over time indicates the agent is improving; increasing indicates drift.

Cost Metrics

  • Cost per task — Total LLM + API costs for a single agent execution. Track by task type for budgeting.
  • Cost per successful task — Same as above, but only counting successful completions. This is your real unit economics number.
  • Retry cost overhead — Additional cost from retried steps and failed tool calls. High overhead means optimization opportunities.

Debugging Agent Failures

When an agent fails, you need to answer three questions fast: What happened? Where in the workflow did it go wrong? Why did the agent make that choice? Good tracing makes all three answerable from a single trace view.

The Debugging Workflow

  1. Start from the root span. Check the overall status and step count. Did the agent complete? Did it hit the step limit? Did it error out?
  2. Find the failing step. Look for the first span with an error status or an unexpected outcome. This is usually (not always) the root cause.
  3. Check the tool call. If the step involved a tool, check the tool call span. Did the tool return an error? Did it return unexpected data? Did the agent misformat the parameters?
  4. Read the reasoning. If you've instrumented reasoning traces, read the agent's rationale for the failing step. Often the bug is in the planning, not the execution.
  5. Check upstream context. Did a previous step provide bad data that caused the later failure? Walk backwards through the trace until you find the actual root cause.
Pro Tip

Build a "trace replay" tool that takes a trace ID and reconstructs the agent's state at each step. Being able to step through an agent execution like a debugger is invaluable when the failure is in the reasoning rather than the code.

Common Root Causes

  • Prompt drift — The system prompt was updated but the agent's behavior assumptions weren't. Shows up as sudden quality drops after deployments.
  • Context pollution — Information from a previous step "leaks" into the agent's reasoning for the current step. Shows up as the agent referencing data it shouldn't have.
  • Tool schema changes — An external API changed its response format. The agent can't parse the new schema and either errors out or misinterprets the data.
  • Model version changes — A model update changes the agent's behavior in subtle ways. Always log the exact model version in every trace.

Production Monitoring Strategy

Debugging individual failures is necessary but not sufficient. In production, you need monitoring that catches systemic issues before they affect users.

Alert on Trends, Not Thresholds

A single agent failure isn't worth an alert. A 15% increase in failure rate over 24 hours is. Configure alerts based on trend deviations from your baselines:

  • Task completion rate drops more than 5% from the 7-day rolling average
  • Average steps per execution increases more than 2x from baseline
  • Tool call error rate exceeds 10% for any single tool
  • P95 end-to-end latency exceeds your SLA threshold
  • Cost per task increases more than 30% from the 30-day average

Dashboard Essentials

Your agent monitoring dashboard should answer these questions at a glance:

  1. Are agents completing tasks? — Task completion rate, error rate, escalation rate
  2. Are they efficient? — Steps per task, tokens per task, cost per task
  3. Are they fast enough? — End-to-end latency percentiles (p50, p95, p99)
  4. Are tools healthy? — Per-tool success rate, latency, and error breakdown
  5. Are guardrails holding? — Guardrail trigger rate and trend
Getting Started

You don't need all of this on day one. Start with three metrics: task completion rate, average steps per execution, and cost per task. These three numbers tell you whether your agent is working, whether it's efficient, and whether it's affordable. Add more granularity as you need it.

The Bottom Line

AI agents are the most complex software systems most teams have ever built. They combine the unpredictability of LLMs with the side effects of traditional software and the autonomous decision-making of, well, nothing we've deployed before at this scale.

The observability challenge is real, but it's solvable. Instrument the agent's trace tree (not just individual calls), capture reasoning alongside actions, track the right metrics, and build alerts that catch systemic issues early.

The teams that invest in agent observability now will be the ones confidently shipping autonomous AI in production. The teams that don't will be the ones writing post-mortems about why their agent sent 10,000 emails at 3 AM.
