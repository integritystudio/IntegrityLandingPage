Integrity Studio · API architecture

API system map

Which Workers serve the product and observability APIs, how a request reaches them, and where API keys and usage data are written. Authentication detail lives in docs/TWO_LAYER_AUTH_ARCHITECTURE.md; contracts and route tables in docs/api-reference.md.

Properties the layout guarantees

  • Two hostnames, two APIs. The product API (api.integritystudio.dev) and the observability API (api.integritystudio.ai) never share a host, so neither repo's routes have to be mirrored in the other's zone config.
  • No public provisioning hop. The receiver is reachable only through the RECEIVER service binding; requests without a known key id, a valid signature, a fresh timestamp and an unseen nonce are rejected.
  • Only obtk_ keys reach the telemetry Workers. They are the only keys with an AUTH KV record. Legacy int_live_ keys, minted by api-gateway, authenticate there and nowhere else.
  • One writer per usage table. api-gateway writes usage_events; a database trigger alone maintains usage_buckets_daily.
  • Quota favours availability. The per-org Durable Object serialises reservations but fails open; the edge throttle in front of org routes is the ceiling that holds when it is unreachable.
