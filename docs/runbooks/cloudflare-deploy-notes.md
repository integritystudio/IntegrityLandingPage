## Versions API — what it settled (2026-07-31)

Each version's detail carries `resources.bindings`, so diffing the **name** sets across versions reconstructs the whole bind/unbind history without ever reading a secret value (values are write-only; only names are returned). Two things this settled that were otherwise guesswork: `SIGNING_KEYS`/`ACTIVE_KEY_ID` were provisioned at **2026-07-30T01:28Z**, not 2026-07-29 as `sender-worker/wrangler.toml` claimed (the stale date was local PDT — the API is UTC, so **record UTC**), which confirms CR01's 2026-07-29 `/send` verification really did exercise `SHARED_SECRET`; and CR15's four stale secrets really were deleted, at 2026-07-31T05:07Z.

`wrangler secret list` and `resources.bindings` count different things — `secret list` returns secrets only, while `resources.bindings` also includes KV, service, and DO bindings, so one worker reads as 13 secrets or 15 bindings. Reconcile before concluding a count disagrees.

## The deploy-token audit (2026-08-03)

The dev/prod deploy split is a config-layer guarantee — but the credential claim that used to sit in CLAUDE.md was wrong three ways. It read "`deploy` and `deploy:prd` both authenticate with the same `CLOUDFLARE_WORKER_TOKEN` from Doppler `prd`". Wrong slot, wrong config, wrong conclusion: `wrangler` authenticates with **`CLOUDFLARE_API_TOKEN`**, `npm run deploy` injects it from Doppler **`dev`** (`doppler run --config dev`) and `deploy:prd` from **`prd`**, and those two values are **distinct** — dev is an account-wide `cfat_` token, prd sha `25889310adec`. The dev token was rotated 2026-08-03 (was `abb57cc474cb`, now `15680a6f90a5`); fingerprint before acting. The byte-identical slot really is `CLOUDFLARE_WORKER_TOKEN` (sha `1243e82a0ae8` in both configs), but **no code in this repo reads it**; its only three readers are `observability-toolkit` workflows, all passing `--config prd`. Same class of error as the `SUPABASE_SERVICE_ROLE_KEY` slot mixup — a doc watching a name that is not the one in play, which is why the fingerprint recipe exists.

**What is still open is scope, not sharing — and distinctness is not scope.** Dev's token is a distinct credential that is not dev-*scoped*: it lists **all 18 Worker scripts in the account**, production `api-gateway` / `sender-worker` / `stripe-webhook` / `obtool-api` / `api-provisioning-receiver` included. `Edit` was not probed, because the probe is a write — but Cloudflare scopes the Workers Scripts permission to the **account**, not to individual scripts, so an `Edit`-carrying token reaches any of them. It is narrower than a global key (`GET /user/tokens` → `Unauthorized`). So what stops `npm run deploy` hitting production is `--env dev` in the script plus `workers/lib/deploy-environments.test.ts` asserting it. **Separate accounts with wrangler profiles pinned per directory remain the only structural fix**; a dev-scoped token narrows blast radius and yields an independently revocable credential, but it cannot make production unreachable. ## Vendor terms — isolation is free (audited 2026-08-02)

Supabase: 2 free projects per owner across all orgs, paused ones uncounted (the pause problem is solved at $0 by `supabase-dev-keepalive.yml`, which pings dev PostgREST Mon+Thu with the publishable key — hardcoded on purpose; anon-class keys are public by design and RLS is on everywhere). ## The propagation incident (2026-07-31)

Immediately after `wrangler secret put STRIPE_PLAN_TO_PRICE_JSON` + `deploy:prd`, a probe with `tier=growth` returned `200` while the very next probe with `tier=starter` returned `no Stripe price configured` — from the *same* secret, whose Doppler value was byte-correct throughout (86 bytes, both keys, verified by dumping it to a file and `JSON.parse`-ing). Different edge nodes were simply on either side of the rollout; a minute later all tiers behaved. The obvious-but-wrong read is "the value was written wrong", which sends you re-`put`ting a secret that was already fine. Same behaviour seen on the CR14 `preview_urls` sweep (one sample showed 42 of 63 closed, the next all 63). Treat it as a general property of Cloudflare config propagation: re-probe before diagnosing, and prefer a loop over a single shot.

## The 2026-07-30 production redeploy

All four production Workers were redeployed from current source, closing a four-month gap; all `200`/healthy afterwards, DO namespace intact, crons and service bindings intact, and — the one that mattered — zone routes unchanged, `api.integritystudio.ai/*` still → `obtool-api`, so CR13's trap did not fire. That is how `stripe-webhook` was caught running a 2026-03-31 build that could not write `webhook_events_log`: binding a secret creates a deployment **without shipping code**, so its deploy timestamps looked fresh while the running code was months old.
